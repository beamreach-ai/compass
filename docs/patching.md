# Patches

Compass follows the CVE feeds, knows which of the account's workloads and which
of the organisation's repositories are affected, and opens the fix pull request
for each. This page says what it follows, what it matches, what it decides, and
what it never does. The design is in
[docs/specs/patching-captain.md](specs/patching-captain.md).

## What it follows

Every hour, without a key or an account:

| Source | What it gives |
|---|---|
| OSV | advisories for the packages on the map, asked by their purls on every run, and the deltas of the ecosystems in use |
| cvelistV5 | every new CVE, kept when it names a product the account runs (PHP, Node, Python, nginx, Apache, Ruby, Go, Redis, Postgres, MySQL, MariaDB, HAProxy, Traefik, Caddy, WordPress, Drupal, OpenSSL) or is already stored |
| CISA KEV | known exploited; the catalogue version is the cursor |
| EPSS | exploitation probability for the stored CVEs, daily |
| Ubuntu, Debian, Alpine, Amazon Linux | which package version in which release is fixed |
| Packagist, npm | the PHP and JavaScript advisories at the source |

Advisories merge on the CVE id into rows of the items table (`CVE#`). A feed
that fails is logged under its name and the others run; the Patches tab shows
each one's last success. `compass patch feed_run` runs them now, the day a
disclosure lands.

## What it matches

The mapper records what every workload is made of as package URLs
(`attributes.software` on the node): the image of each container in a task
definition, a Lambda's runtime and layers, an instance's AMI and packages, and
in the repositories the Dockerfiles, manifests, lockfiles, serverless and SAM
descriptors and Terraform. Every fifteen minutes the match holds each entry
against the advisories, in the ecosystem's own version order (dpkg's for deb
and apk, rpm's, PEP 440, semver), and writes a finding per advisory, node and
package: the fixed version, the repository and file, the workloads that run
what the file builds (through the repository's image repositories on the map)
and whether any of them faces the internet.

A finding says what stands in the way of a plain bump: no fixed version yet, a
floating image tag, a transitive dependency, a major upgrade, a Bref layer
whose exact PHP patch release is not known.

## What it decides

Two outcomes, re-decided every tick as KEV, EPSS and exposure change:

- **A pull request without a click** when the vulnerability is in KEV, its EPSS
  is at or above 0.1, its CVSS is at or above 7.0 (or its label is high or
  critical when no score is published), or the workload faces the internet, and
  nothing stands in the way of a plain bump.
- **An inbox item** otherwise, one per repository: "Open the pull request for
  4 findings in acme/api". Approving it opens the same pull request.

The thresholds live in the workspace config under `patch.act_on`; `patch.ignore`
silences an advisory until a date with a reason. The PR watcher's policy and the
access model's grants are the only other controls.

```json
"patch": {
  "act_on": {"kev": true, "epss_min": 0.1, "cvss_min": 7.0, "exposed": true},
  "repos": [],
  "max_open_prs": 10,
  "ignore": [{"advisory": "CVE-2026-109618", "until": "2026-12-01", "reason": "mitigated at the WAF"}]
}
```

## What it fixes

One pull request per repository, on `beamreach/patch/<yyyymmdd>-<short>`,
with every fix that repository needs, regenerated from the base branch when
new findings land before it merges. Every edit is deterministic: a version
string replaced by the one the advisory names.

| Software | The edit |
|---|---|
| `FROM php:8.3.30-fpm` (any docker-library tag) | the same tag at the fixed upstream version; a digest-pinned `FROM` gets the new tag's digest from Docker Hub, or loses the pin and the body says so |
| `apt-get install php8.3-fpm` on Ubuntu or Debian | pinned to the fixed distro version (`php8.3-fpm=8.3.6-0ubuntu0.24.04.13`), or its pin replaced |
| `apk add php83` on Alpine | the same, with Alpine's version |
| a Bref or other layer ARN in `serverless.yml`, a SAM template or Terraform | the layer version |
| a direct dependency in `composer.json`, `package.json`, `requirements*.txt`, `pyproject.toml`, `go.mod`, `Cargo.toml` | the lowest fixed version, the constraint's prefix kept; the lockfile is regenerated by the repository's CI |

The body lists each finding (advisory, package, from → to, the workload and
whether it faces the internet, CVSS, KEV, EPSS), the changes per file, what
verification applies, and how to roll back (revert the pull request). With a
model configured, one paragraph explains the vulnerability from the advisory's
own text; without one, the template stands. Labels: `compass:patch`,
`security`, and `compass:exploited` when the vulnerability is in KEV.

The pull request is registered with the PR watcher, which syncs it, answers
reviewers and revises within the touched files. A merge moves the findings to
`merged`; the next scan that sees the fixed version running moves them to
`deployed`. A pull request closed without merging sends its findings back to
`open` and opens no new pull request for fourteen days. `patch.max_open_prs`
bounds how many are open at a time; `patch.repos` and `prs.watcher.repos` say
where they may open. `compass patch pr repo=acme/web` opens one now.

What it does not do yet: bump a Lambda runtime or an AMI, move a transitive
dependency, or cross a major version; those findings wait in the inbox with
the reason said.

## What it verifies

Three steps, each recorded on the finding and told to the pull request, each
able to keep it from being called ready:

1. **CI**: the repository's checks on the pull request's head, as the PR
   watcher reads them. Red marks the pull request `needs_you` with the failing
   check's name.
2. **The image build**, where the fix touched a Dockerfile: the check of the
   workflow that builds it. Compass has no Docker socket by design, so the
   build runs where the repository builds. When no workflow of the repository
   builds an image on pull requests, the pull request adds
   `.github/workflows/compass-build.yml`, which builds each changed Dockerfile
   with BuildKit and does not push; keep it or replace it with your own.
3. **The canary**, when the workspace named a staging twin for the service and
   the grant `patch.canary_deploy` is armed: a task definition revision with
   the pull request's image (`pr-<sha>` in the production image's ECR
   repository, pushed by your build workflow), the staging service updated to
   it, steady state awaited, the target group's health path and your probe
   paths fetched for the window and compared with what the service answered
   before, 5xx and p95 latency compared with the five minutes before through
   CloudWatch, then the staging service rolled back to its previous revision.
   The result is a comment on the pull request. A failed canary marks the pull
   request `needs_you` with `canary_failed`. Without a twin, a grant or a
   `pr-<sha>` image the canary is skipped and the pull request says so; it is
   still ready on CI and the build.

### Naming a canary

```json
"patch": {
  "canaries": {
    "web": {"staging_service": "web-staging", "cluster": "staging", "probe_paths": ["/", "/health"], "minutes": 5,
            "task_role_arns": ["arn:aws:iam::123456789012:role/web-task"]}
  }
}
```

The key is the production service's name on the map; `staging_service` is the
twin's name in `cluster` (or its ARN). The first tick after this is saved
proposes the grant `patch.canary_deploy` with statements scoped to exactly
those staging services and clusters (`ecs:UpdateService` and
`ecs:DescribeServices` on the twins, `ecs:RegisterTaskDefinition`,
`iam:PassRole` on the named task roles, the load balancer and CloudWatch
reads); accept it on the Access page or from the inbox, merge its pull request,
and the canary runs from the next green pull request. The action never touches
the service that serves traffic. See [access.md](access.md).

## States

```
open ──(pull request)──▶ pr_open ──(merge)──▶ merged ──(the map shows the fix running)──▶ deployed
  │  (inbox, approved) ──▶ approved ──▶ pr_open …
  └──(a person, with a reason, until a date)──▶ ignored
any ──(the inventory no longer matches)──▶ closed
```

A finding closes itself when the inventory no longer matches; one whose pull
request merged becomes `deployed` when the next scan sees the fix running.

## The tab, the API, the commands

The Patches tab lists the findings with their severity, KEV and EPSS, the fix
version, the workloads and repository, the verdict and the state, with filters
for exposed, exploited and waiting for merge; its "Needs you" view is the inbox
for this tab. `GET /api/patches` is the same in one call; `POST
/api/patches/findings/approve`, `…/ignore`, `…/{key}/reopen` are a person's
decisions; `POST /api/patches/feed/run` and `/api/patches/tick` start the jobs.
`compass patch findings [state=…] [exposed=true] [exploited=true] [repo=…]`,
`compass patch tick`, `compass patch approve keys=[…]`, `compass patch ignore key=…
until=… reason=…`, `compass patch feed_status`, `compass patch inventory`.

## What it never does

It never patches a running image in place, never merges, and never touches a
site Compass cannot see: a host outside AWS, a repository the mapper does not
read. A container-image Lambda's image is not read (that needs
`lambda:GetFunction`, which the access model forbids); the node says
`packageType: Image` so the gap is visible.
